# vllm / vllm-ascend 精度问题追踪与案例整理

维护本地精度问题知识库：增量收集两仓库的精度问题，筛选「必现 + 已修复」者整理为可复现案例。

## 知识库位置与结构

```
vllm-ascend/0_topic/precision/
├── 0_overview.md    # 体系总览 / 导航（三梯队 + 共同脉络 + 索引）
├── 0_precision.md   # ① 全景统计：全部精度问题分类条目
├── 0_kvcache.md     # ② KV Cache 专题：KV 相关精度问题
└── cases/           # ③ 必现案例集（编号 = 复现难度从易到难）
    ├── README.md    # 索引 + 复现前置 + 共同脉络 + 候选留档（C 编号）
    ├── 1_单机单卡/  # 一张 NPU 卡（甚至 CPU）可复现
    ├── 2_单机多卡/  # 单节点 2~16 卡
    └── 3_多机多卡/  # 多节点 PD 分离（≥2 节点 + Mooncake）
```

**开工第一步**：先读 `cases/README.md`，掌握当前已有案例编号、候选留档（C 编号）与索引状态——**所有数量、编号一律以文件当前内容为准，不要凭记忆**。

## 三条工作流（按用户意图分流）

### 工作流 A · 增量收集精度问题

用户说「收集/更新精度问题」「检索新的精度 bug」时走此流程。

1. **确定检索窗口**：从上次整理日期（见 0_overview.md 文末「整理时间」）到今天。
2. **检索渠道**（优先并行子代理，每个不超过 6 条结果）：
   - WebSearch：`vllm-ascend accuracy fix github`、`vllm-ascend quantization precision PR`、`vllm wrong output NaN issue` 等；
   - WebFetch 抓具体 PR/issue 页面（`https://github.com/vllm-project/vllm-ascend/pull/{n}`）；
   - GitHub API 遇 403 rate-limit 时分批拉取 + 本地缓存。
3. **关键词族**：精度 / accuracy / precision / wrong output / NaN / Inf / garbled / 乱码 / 重复输出 / 接受率下降（acceptance）/ 输出发散 / GSM8K 分数崩塌。
4. **降噪规则**：
   - 短词（`inf`、`nan`）用词边界正则 `\bnan\b|\binf(?:inity|inite)?\b`，避免子串误匹配；
   - 生成 Markdown 表格时标题里的 `|` 必须转义。
5. **归册**：新条目写入 `0_precision.md` 对应分类；KV Cache 相关的同步进 `0_kvcache.md`；更新统计数字与整理时间。

### 工作流 B · 整理可复现案例

用户说「整理案例」「这个 case 帮我写一下」时走此流程。

**① 收录门槛（三条全满足才成为正案例）**：

| 门槛 | 判据 |
|------|------|
| 必现 | 有明确触发条件矩阵（通常 2~3 个条件组合同时成立才触发） |
| 已修复 | PR merged，或 issue closed 且能给出修复 PR 链接 |
| 精度类 | 输出错误 / 精度退化 / NaN / 接受率崩塌；纯性能问题不收，崩溃但根因是数值/布局错位可收 |

不满足者进「候选留档」（C 编号），注明缺哪条门槛、满足后如何提升。

**② 去重**：对照 cases/README.md 索引表与候选留档的编号清单，已收录的禁止重复整理。

**③ 信息采集（逐条亲自核验，禁止编造）**：
- 现象 / 触发矩阵 / 影响与严重度（🔴 极高/高、🟡 中）；
- **版本信息**：vllm-ascend 版本 + 上游 vLLM 版本（PR 描述通常写 "vLLM version/main commit"）——查不到写「未知」，**不许编造**；
- 定位过程（无则写「未知」）；
- 根因 / 关键 diff / 验证方式；
- 复现方法。

**④ 最小复现原则**：
- 尽量选小模型（<10B 优先，w8a8 量化版次之）；单卡 > 多卡 > 多节点；
- **模型必须真支持触发特性**——写之前用本地仓库 CI 配置核实（`vllm-ascend/tests/e2e/**/*.yaml`，看该特性用哪些模型）；例如带 MTP 的家族只有 Qwen3.5 / DeepSeek / GLM；
- 复现章节**只写「用什么模型 + 怎么复现」**，不要写「XX 模型不能用」之类的排除说明；
- PD 分离案例给 P/D 双端命令骨架，注明 kv_port ≥ 36000（避开 AscendDirect RDMA 随机端口）。

**⑤ 归档与编号**：
- 按复现难度选梯队文件夹：`1_单机单卡` / `2_单机多卡` / `3_多机多卡`；
- 编号即难度顺序：新案例插入梯队尾部；若要插中段则需重排后续编号——用**两步重命名法**（先全部改成 `__tmp__` 前缀临时名，再改最终名）避免目标名冲突；批量操作用 Python 脚本（PowerShell 中文编码易出错）；
- 同步更新：cases/README.md（索引表 + 案例文件清单 + 复现前置）、0_overview.md（目录树 + 梯队表 + 索引）。

**⑥ 案例文件命名**：`{编号}_{pr|issue}{编号}_{主题小写蛇形}.md`，例：`07_pr9036_routed_scaling_factor.md`。

### 工作流 C · 候选留档跟进

用户说「跟进候选」「看看哪些能转正」时走此流程。

1. 逐条核验候选留档里的修复 PR 状态；
2. 已 merged 的按工作流 B 提升为正案例（补齐五段信息）；
3. 从候选表删除已提升项，更新案例计数与整理时间。

## 硬性规则

1. **亲自核验**：每个案例的 PR/issue 必须逐条 WebFetch 确认状态与内容，禁止凭搜索摘要或记忆写结论。
2. **版本双仓库**：vllm 与 vllm-ascend 版本都要查；查不到写「未知」，绝不编造。
3. **NPU 可复现性**：只在 NVIDIA kernel 路径存在的问题（如 FlashInfer TRTLLM）不收录，可作候选注明原因。
4. **不重复**：整理前先对照索引去重。
5. **文件间交叉链接**：移动/重命名案例文件前，先 `rg "](./" ` 检查相对链接，防止断链。
