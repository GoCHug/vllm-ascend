## 二、浮点数基础原理

### 2.1 区间划分思想

计算机中浮点数的表示，核心思想是**以2的幂次方划分区间**。

以正数为例（负数可以通过符号位简单扩展）：

```
区间1: [2^-2, 2^-1) = [0.25, 0.5)
区间2: [2^-1, 2^0)  = [0.5, 1)
区间3: [2^0, 2^1)   = [1, 2)
区间4: [2^1, 2^2)   = [2, 4)
区间5: [2^2, 2^3)   = [4, 8)
区间6: [2^3, 2^4)   = [8, 16)
...
```

> 注意：所有区间都是**左闭右开** `[start, end)`。

### 2.2 具体示例：9.23 如何表示？

**第一步：确定大区间**

9.23 位于区间 `[8, 16)`，即 `[2^3, 2^4)`。
- 大区间起点 = 8 = 2^3
- 9.23 比 8 大 1.23

**第二步：大区间均匀分割**

将 `[8, 16)` 这个长度为8的区间，均匀分割成 **1024份**（2^10份）。

- 每份长度 = 8 / 1024 = 2^-7 ≈ 0.0078125
- 小区间起点：0×S, 1×S, 2×S, ..., 1023×S

**第三步：找到最近的小区间**

1.23 / 0.0078125 ≈ 157.44，即1.23位于第157个小区间附近。

- 157 × S = 157 × 2^-7 = 157 / 128 ≈ 1.2266

**第四步：近似表示**

```
9.23 ≈ 8 + 1.2266 = 9.2266
```

> **精度损失的本质**：9.23 并不是离散点上的精确值，只能用最近的点 9.2266 来近似表示，差值 0.0034 就是精度损失。

### 2.3 二进制存储方式

实际计算机中用二进制存储，不会存十进制的"8"和"157"，而是：

| 组成部分 | 二进制示例 | 含义 |
|----------|-----------|------|
| 指数部分 | `011` | 表示 2^3 = 8（大区间起点） |
| 尾数部分 | `0010011101` | 表示157（第几个小区间） |

### 2.4 不同数据类型的来源

浮点数的区间划分有两个关键参数可以变化：

1. **区间从哪里开始？** 可以从 2^-2 开始，也可以从 2^-10 开始
2. **每个大区间分成多少份？** 可以分1024份，也可以分2048份、4096份

这两个参数的不同组合，就衍生出了不同的浮点数类型：

- **FP16**（Half Precision）：16位
- **BF16**（Brain Float 16）：16位
- **FP32**（Single Precision）：32位
- **FP64**（Double Precision）：64位

> 理论上数据类型可以有无穷多种，但为了硬件计算的统一性和各家交流的便利性，实际只定义了常用的几种。

## 三、FP16 数据类型详解

FP16（Float 16，半精度浮点数）是PyTorch中最常用的数据类型之一。

### 3.1 FP16 的位结构

FP16 总共 **16位（2字节）**，分为三部分：

```
[1位符号位] [5位指数位] [10位尾数位]
   S           EEEEE         MMMMMMMMMM
```

| 部分 | 位数 | 作用 |
|------|------|------|
| 符号位(S) | 1位 | 0=正数，1=负数，不参与数值计算 |
| 指数位(E) | 5位 | 确定大区间（2的多少次方） |
| 尾数位(M) | 10位 | 确定在大区间中的第几个小区间 |

### 3.2 指数位详解

5位二进制可以表示 2^5 = 32 个数（0~31）。

- **全0（00000）和全1（11111）** 作为特殊符号（表示0、无穷大、NaN等），不参与正常数值表示
- 实际可用：32 - 2 = **30个区间**

这30个区间的指数范围定义为：**2^-14 到 2^15**

```
第1个区间:  [2^-14, 2^-13)
第2个区间:  [2^-13, 2^-12)
...
第15个区间: [2^0,  2^1)   = [1, 2)
...
第30个区间: [2^14, 2^15)
```

> 这是一种**规定**（标准定义），因为这样的数值范围最为常用。理论上也可以定义为 2^-15 到 2^14，但不常用。

### 3.3 尾数位详解

10位二进制可以表示 2^10 = 1024 个数（0~1023）。

- 每个大区间被均匀分割成 **1024个小区间**
- 尾数位的值决定了使用第几个小区间的起点

### 3.4 数值计算示例

**示例：FP16 能表示的最大正数**

```
符号位 = 0（正数）
指数位 = 11110 = 30 → 对应第30个区间 [2^14, 2^15) = [16384, 32768)
尾数位 = 1111111111 = 1023 → 第1023个小区间

大区间起点 = 2^15 = 32768
小区间偏移 = 1023/1024 × 2^15 = 1023/1024 × 32768 ≈ 32736

最大值 = 32768 + 32736 = 65504
```

> **FP16 最大正数 = 65504**

### 3.5 核心结论：数值越大，精度越低

这是浮点数最重要的性质之一。

**原理分析：**

```
小区间宽度 = 大区间长度 / 1024

大区间 [2^k, 2^(k+1)) 的长度 = 2^k
所以小区间宽度 = 2^k / 1024 = 2^(k-10)
```

| 大区间 | 大区间长度 | 小区间宽度 | 精度 |
|--------|-----------|-----------|------|
| [1, 2) | 1 | 1/1024 ≈ 0.000977 | 高 |
| [8, 16) | 8 | 8/1024 ≈ 0.007813 | 中 |
| [1024, 2048) | 1024 | 1024/1024 = 1 | 低 |
| [32768, 65536) | 32768 | 32768/1024 = 32 | 很低 |

**通俗类比**：
- 骑自行车速度慢，可以精确到前进1厘米、2厘米
- 开火车速度快，精确距离可能就是10米、20米

### 3.6 代码验证

```python
import torch

# FP16 表示 9.23
a = torch.tensor(9.23, dtype=torch.float16)
print(a)  # 输出: tensor(9.2266, dtype=torch.float16)

# FP16 表示 9.23001
b = torch.tensor(9.23001, dtype=torch.float16)
print(b)  # 输出: tensor(9.2266, dtype=torch.float16)

# 两者相等！因为精度不足，差异被忽略
print(a == b)  # 输出: True
```

### 3.7 特殊值

指数位的全0和全1用于表示特殊值：

| 指数位 | 含义 |
|--------|------|
| 全0 (00000) | 零值、非规格化数 |
| 全1 (11111) | 正无穷(+inf)、负无穷(-inf)、NaN |

## 四、FP32 数据类型与上溢出

### 4.1 FP32 的位结构

FP32（Float 32，单精度浮点数）总共 **32位（4字节）**：

```
[1位符号位] [8位指数位] [23位尾数位]
   S         EEEEEEEE    MMMMMMMMMMMMMMMMMMMMMMM
```

| 部分 | 位数 | FP16对比 | 作用 |
|------|------|----------|------|
| 符号位(S) | 1位 | 相同 | 0=正数，1=负数 |
| 指数位(E) | 8位 | FP16是5位 | 确定大区间，范围大很多 |
| 尾数位(M) | 23位 | FP16是10位 | 分割更细，精度更高 |

### 4.2 FP32 vs FP16 对比

| 特性 | FP16 | FP32 |
|------|------|------|
| 总位数 | 16位 | 32位 |
| 字节数 | 2字节 | 4字节 |
| 指数位 | 5位 | 8位 |
| 尾数位 | 10位 | 23位 |
| 可表示区间数 | 30个 | 254个 |
| 小区间分割数 | 1024 | 8,388,608 (2^23) |
| 最大正数 | 65504 | ≈3.4×10^38 |
| 精度 | 较低 | 高 |

### 4.3 精度对比代码验证

```python
import torch

# FP16
a16 = torch.tensor(9.23, dtype=torch.float16)
b16 = torch.tensor(9.231, dtype=torch.float16)
print(f"FP16: 9.23={a16.item()}, 9.231={b16.item()}, 相等={a16==b16}")
# FP16 无法区分 9.23 和 9.231

# FP32
a32 = torch.tensor(9.23, dtype=torch.float32)
b32 = torch.tensor(9.231, dtype=torch.float32)
print(f"FP32: 9.23={a32.item()}, 9.231={b32.item()}, 相等={a32==b32}")
# FP32 可以精确区分
```

### 4.4 上溢出（Overflow）

#### 4.4.1 什么是上溢出？

当数值超过了数据类型能表示的最大值时，就会发生**上溢出**，数值变为无穷大（inf）。

#### 4.4.2 FP16 的溢出边界

```python
import torch

# FP16 最大正数
max_val = torch.tensor(65504, dtype=torch.float16)
print(max_val)  # 65504.0

# 65505 不会立即溢出！仍然表示为 65504
val = torch.tensor(65505, dtype=torch.float16)
print(val)  # 65504.0（精度折损，不是溢出）

# 真正的溢出点：2^16 = 65536
overflow_val = torch.tensor(65536, dtype=torch.float16)
print(overflow_val)  # inf（上溢出！）
```

#### 4.4.3 为什么 65505 不会溢出？

FP16 最后一个大区间是 `[2^15, 2^16) = [32768, 65536)`，分成1024个小区间：

- 第1023个小区间起点 = 32768 + (1023/1024)×32768 = 65504
- 65505、65506、... 都落在第1023个小区间内，都表示为65504
- 只有超过 65536（2^16）才会真正溢出为 inf

> **关键区别**：65505~65535 是**精度折损**（表示为65504），≥65536 才是**上溢出**（变为inf）。

## 五、数值问题：下溢出、NaN 与实战

### 5.1 下溢出（Underflow）

#### 5.1.1 什么是下溢出？

当数值非常小，小于数据类型能表示的最小正数时，就会发生**下溢出**，数值被表示为0。

#### 5.1.2 下溢出的危害

```python
import torch

# 极小的数
c = torch.tensor(1e-10, dtype=torch.float16)
print(c)  # 0.0（下溢出！）

d = torch.tensor(1.0, dtype=torch.float16)
e = d / c
print(e)  # inf（1除以0 = 无穷大，连锁反应！）
```

> 下溢出本身可能不致命，但它会导致**除零错误**，进而引发上溢出，最终产生NaN。

### 5.2 BF16 数据类型

#### 5.2.1 BF16 的结构

BF16（Brain Float 16）是Google提出的16位浮点数格式：

```
[1位符号位] [8位指数位] [7位尾数位]
```

| 部分 | FP16 | BF16 | FP32 |
|------|------|------|------|
| 总位数 | 16 | 16 | 32 |
| 指数位 | 5位 | **8位** | 8位 |
| 尾数位 | 10位 | **7位** | 23位 |

#### 5.2.2 BF16 的特点

- **指数位8位**：与FP32相同，能表示的数值范围和FP32一样大（最大约3.4×10^38）
- **只有2字节**：比FP32节省一半显存
- **尾数位只有7位**：精度比FP16还差

> **为什么大模型大量使用BF16？** 主要是为了能表示比较大的数（避免attention中指数运算的上溢出），同时节省显存。代价是精度较低。

#### 5.2.3 BF16 的问题

由于尾数位少，BF16精度很差，**容易发生下溢出**。在需要高精度的场景（如梯度计算、归一化）中，BF16可能不够用。

### 5.3 NaN 的产生原因与排查

NaN（Not a Number）是大模型训练中最常见的问题之一。

#### 5.3.1 原因一：Softmax / Sigmoid 上溢出

```python
import torch

def naive_softmax(x):
    """朴素的softmax实现，容易溢出"""
    exp_x = torch.exp(x)
    return exp_x / exp_x.sum()

# 输入数值较大时
x = torch.tensor([1000.0, 1001.0], dtype=torch.float16)
result = naive_softmax(x)
print(result)  # tensor([nan, nan]) —— exp(1000) 上溢出为 inf，inf/inf = nan
```

**解决方案：减去最大值**

```python
def stable_softmax(x):
    """数值稳定的softmax"""
    x_max = x.max()
    exp_x = torch.exp(x - x_max)  # 每项减去最大值
    return exp_x / exp_x.sum()
```

> 这有严格的数学推导，感兴趣的同学可以自行研究。

#### 5.3.2 原因二：BatchNorm / LayerNorm 中的下溢出

归一化公式：`(x - mean) / std`

- 当 batch size 很小，且样本数值相近时，方差(std)趋近于0
- 方差下溢出为0 → 除以0 → 上溢出 → NaN

> batch size = 1 时，方差必然为0，必然出问题。

#### 5.3.3 原因三：求平均值时求和溢出

```python
import torch

# 10个元素，每个1000，求平均
arr_small = torch.full((10,), 1000.0, dtype=torch.float16)
print(arr_small.mean())  # 约999.5（有精度损失，但正常）

# 50万个元素，每个1000，求平均
arr_large = torch.full((500000,), 1000.0, dtype=torch.float16)
print(arr_large.mean())  # nan —— 先求和：500000×1000=5e8 > 65504，上溢出！
```

#### 5.3.4 原因四：Loss 求和时 batch size 过大

训练时，总loss = 各个样本的loss相加。

- batch size 特别大时，loss总和可能溢出
- 这也是为什么大batch size训练容易出NaN

#### 5.3.5 NaN 排查清单

当训练出现NaN时，按以下顺序排查：

| 排查项 | 检查内容 | 解决方案 |
|--------|----------|----------|
| 1. 输入数据 | 是否有异常大的值？ | 输入归一化（如CV中0-255归一化到-1~1） |
| 2. Batch Size | 是否设得太大？ | 减小batch size |
| 3. Batch Size | 是否设得太小（如=1）？ | 增大batch size，或使用LayerNorm替代 |
| 4. 指数运算 | Softmax/Attention是否稳定？ | 使用减去最大值的稳定实现 |
| 5. 数据类型 | 是否全用FP16/BF16？ | 关键计算用FP32 |

### 5.4 为什么CV中要做输入归一化？

计算机视觉中，像素值通常是0~255。如果直接输入网络：

- 255作为输入已经较大
- 网络层数加深后，数值层层放大
- 最终可能直接溢出为NaN

所以通常会将像素归一化到 `[-1, 1]` 或 `[0, 1]`，其中一个重要考虑就是**数值稳定性**。

### 5.5 本质总结

大模型训练中各种数值问题的根本原因：

> **计算机的数值表达精度不够，或者表示范围不够。**

但你又不能无限增大精度（如全用FP64），因为那样显存占用会非常大。这就是大模型难以训练的核心矛盾之一。

## 六、模型显存占用与混合精度训练

### 6.1 全量微调的显存占用计算

以 **GPT-2 1.5B** 模型为例，计算全量微调所需显存。

#### 6.1.1 各部分显存

| 组件 | 数据类型 | 每个参数字节数 | 1.5B参数总显存 |
|------|----------|---------------|----------------|
| 模型参数(W) | FP16 | 2字节 | 2 × 1.5G = **3GB** |
| 梯度(G) | FP16 | 2字节 | 2 × 1.5G = **3GB** |
| 一阶动量(m) | FP32 | 4字节 | 4 × 1.5G = **6GB** |
| 二阶动量(v) | FP32 | 4字节 | 4 × 1.5G = **6GB** |
| **合计** | | | **约18GB** |

> 加上激活值、临时变量等，实际训练约需 **24GB** 显存。

#### 6.1.2 关键要点

- **Adam优化器的动量状态(m, v)必须用FP32**，不能用FP16
- 推理时只需要模型参数：**3GB**
- 全量微调显存 ≈ 推理的 **8倍**
- 这就是为什么 **LoRA** 等参数高效微调方法如此流行——显存不够！

### 6.2 大数加小数问题（舍入误差）

#### 6.2.1 问题描述

当一个大数加上一个非常小的数时，由于精度限制，小数可能被"吃掉"，加了等于没加。

```
大数位于大区间 → 小区间宽度大 → 小数小于小区间宽度 → 加法无效果
```

#### 6.2.2 代码验证

```python
import torch

# 基础数值
x16 = torch.tensor(3.141, dtype=torch.float16)
x32 = torch.tensor(3.141, dtype=torch.float32)

print(f"FP16: 3.141 -> {x16.item()}")  # 3.1406（精度损失）
print(f"FP32: 3.141 -> {x32.item()}")  # 3.141（精确）

# 加上一个小数
delta = 0.0005
y16 = x16 + delta
y32 = x32 + delta

print(f"FP16: 3.141 + 0.0005 = {y16.item()}")  # 3.1406（加了等于没加！）
print(f"FP32: 3.141 + 0.0005 = {y32.item()}")  # 3.1415（正常）
```

#### 6.2.3 对训练的影响：Loss 不再下降

参数更新公式：

```
W_new = W_old + lr × gradient
```

- 训练后期 / 微调时，学习率(lr)很小
- 梯度(gradient)也很小
- `lr × gradient` 非常小
- 如果 W 用 FP16 存储，`lr × gradient` 可能小于小区间宽度
- **加了等于没加 → Loss不再下降！**

> 注意：这不是真的不再下降，而是**数值精度损失导致的假象**。

### 6.3 梯度下溢问题

训练后期，大量梯度变得非常小：

- 67%的梯度可能小于FP16能表示的最小正数
- 这些梯度**下溢变为0**
- 相当于大量参数没有得到更新

### 6.4 FP16 训练的三大问题总结

| 问题 | 原因 | 表现 |
|------|------|------|
| **梯度下溢** | 梯度太小，小于最小可表示值 | 大量梯度变0，训练停滞 |
| **激活上溢** | 指数运算（Softmax/Attention）数值太大 | 出现inf，进而NaN |
| **舍入误差** | 大数加小数，小数被吃掉 | Loss不下降，参数更新无效 |

### 6.5 解决方案：损失缩放（Loss Scaling）

损失缩放是混合精度训练的核心技术之一。

#### 6.5.1 核心思想

```
把损失人为放大 → 梯度也被放大 → 避免梯度下溢
更新参数前再缩小回去 → 保证更新量正确
```

#### 6.5.2 完整流程

```
┌─────────────────────────────────────────────────────────┐
│                    混合精度训练流程                        │
├─────────────────────────────────────────────────────────┤
│                                                           │
│  1. 前向传播                                              │
│     模型参数(FP16) → 计算Loss                             │
│     Loss 必须用 FP32 保存（否则直接下溢）                 │
│                                                           │
│  2. 损失放大                                              │
│     scaled_loss = loss × scale_factor                     │
│     （scale_factor 如 128, 1024, 65536 等）             │
│     只要不发生上溢出，越大越好                             │
│                                                           │
│  3. 反向传播求梯度                                        │
│     梯度 = d(scaled_loss)/dW = scale_factor × d(loss)/dW│
│     梯度被放大了 scale_factor 倍 → 不会下溢！             │
│     梯度可以用 FP16 存储                                   │
│                                                           │
│  4. 梯度缩小                                              │
│     gradient = gradient / scale_factor                    │
│     ⚠️ 必须先转成 FP32 再缩小！                           │
│     （如果用FP16缩小，精度会被干掉，又下溢了）             │
│                                                           │
│  5. 参数更新                                              │
│     W_new = W_old - lr × gradient（FP32计算）            │
│     更新后转回 FP16 存储                                   │
│                                                           │
└─────────────────────────────────────────────────────────┘
```

#### 6.5.3 为什么不直接全用FP32？

| 方案 | 显存占用 | 计算速度 |
|------|----------|----------|
| 全FP32训练 | 大（约2倍FP16） | 慢 |
| 混合精度（FP16+FP32） | 小 | 快（大部分计算用FP16） |

混合精度训练在**几乎不损失精度**的前提下，大幅节省显存并提升训练速度。

#### 6.5.4 关键注意事项

1. **Loss必须用FP32**：前向计算出的loss如果直接用FP16保存，可能已经下溢为0，之后再放大也没用
2. **梯度缩小前必须转FP32**：如果用FP16直接除以scale_factor，精度会直接损失，又下溢了
3. **scale_factor的选择**：动态调整，太大会上溢，太小防不住下溢。现代框架（如PyTorch AMP）会自动调整

## 七、附录A：大模型的本质局限——没有逻辑能力

### 7.1 大模型的本质

大模型本质上是一个**概率自动机**，它的数据处理强调的是**相关性**，而不是**因果性**。

> 从根本上来说，大模型**没有逻辑推理能力**。

### 7.2 "1+1=2" 的真相

普通人以为大模型会做 `1+1=2`，但实际上：

```
输入字符序列: "1" "+" "1" "="
大模型根据统计规律: 99.8%的情况下，下一个字符是 "2"
输出: "2"
```

这不是计算出来的，而是**统计出来的**。

### 7.3 经典错误：9.11 > 9.9

大模型有时会认为 `9.11 > 9.9`，原因是：

- 大部分情况下，"11" > "9"（作为整数比较）
- 大模型根据统计相关性，错误地将这个规律套用到小数比较上

### 7.4 相关性 vs 因果性

| | 机器学习（大模型） | 人类智能 |
|---|---|---|
| 基础 | 相关性（统计规律） | 因果性（逻辑推理） |
| 决策依据 | 数据中出现频率高的就是"对的" | 基于因果律推导 |
| 例子 | "人多的就是真理" | 虚数根据因果律发明，不因多数人不知道而错误 |

> 世界上至少有一半人不知道什么是虚数，难道虚数就是错误的吗？当然不是。

### 7.5 思维链（CoT）的局限

目前的思维链（Chain-of-Thought）技术：

- 人工输入碎片化的逻辑事件模板
- 让大模型"套模板"来回答
- **无法从本质上解决因果性问题**
- 该错的还是会继续错

## 八、附录B：微调的困境与解决方案

### 8.1 灾难性遗忘（Catastrophic Forgetting）

在基座大模型上直接用垂直数据微调，会出现：

- ✅ 在微调数据上：性能变好
- ❌ 在其他原始能力上：性能明显下降

这就是**灾难性遗忘**。而且两者之间极难通过微调来平衡。

### 8.2 为什么微调难以平衡？

由于计算力、训练时间、数据量等因素限制：

- 只能对**部分参数**进行快速微调
- 放弃对所有数据或模型参数的完整调整
- 模型被分割成两个部分：**原始基础部分** + **微调部分**

这种形态很难让模型从底层形成反应整体能力的**有机体**。

> 类比：人的身体肾脏不好，可以器官移植来缓和病症，但这肯定不是对整个有机体最有效的治疗方式。从这个角度看，微调只能是**治标不治本**。

### 8.3 解决方案

#### 方案一：混合通用知识训练

在训练数据中，垂直数据混合一些通用知识进行训练，避免模型完全遗忘基础能力。

#### 方案二：外挂知识库（RAG）

不修改模型参数，而是使用**检索增强生成（RAG）**的方式：

- 外部知识库存储垂直领域知识
- 推理时检索相关知识，注入到prompt中
- 模型本身保持不变，不会产生灾难性遗忘

## 九、关键要点总结

### 9.1 浮点数核心概念

| 概念 | 要点 |
|------|------|
| 区间划分 | 以2的幂划分大区间，每个大区间均匀分割为小区间 |
| 精度损失 | 离散点无法精确表示所有实数，只能近似 |
| 数值越大精度越低 | 大区间越宽→小区间越宽→精度越差 |
| 上溢出 | 超过最大值→inf |
| 下溢出 | 小于最小正数→0 |

### 9.2 数据类型对比

| 类型 | 总位 | 指数位 | 尾数位 | 最大正数 | 特点 |
|------|------|--------|--------|----------|------|
| FP16 | 16 | 5 | 10 | 65504 | 省显存，范围小，精度中等 |
| BF16 | 16 | 8 | 7 | ≈3.4×10^38 | 省显存，范围大，精度差 |
| FP32 | 32 | 8 | 23 | ≈3.4×10^38 | 范围大，精度高，占显存 |

### 9.3 训练问题与解决方案

| 问题 | 原因 | 解决方案 |
|------|------|----------|
| NaN | 上溢出/下溢出连锁反应 | 检查输入、batch size、使用稳定softmax |
| Loss不下降 | 大数加小数的舍入误差 | 使用FP32做参数更新，混合精度训练 |
| 梯度消失 | 梯度下溢为0 | 损失缩放（Loss Scaling） |
| 显存不足 | 全量微调参数+梯度+优化器状态 | 使用LoRA等参数高效微调方法 |

### 9.4 混合精度训练关键步骤

1. 前向计算，Loss用**FP32**保存
2. Loss放大（×scale_factor），避免梯度下溢
3. 反向传播，梯度可用**FP16**
4. 梯度转**FP32**后缩小（÷scale_factor）
5. FP32更新参数，转回FP16存储

### 9.5 大模型本质认知

- 大模型是**概率自动机**，基于相关性而非因果性
- 没有真正的逻辑推理能力
- 微调存在**灾难性遗忘**，治标不治本
- RAG是比纯微调更可靠的垂直领域落地方案
